# Подключение и сборка

Команды выполняются из корня репозитория. SDK предназначен только для Kotlin/Native **2.1.21** и Windows x64 (`mingw_x64`), результат — Windows DLL. Ревизия клиента и SHA256 заголовка закреплены в [sdk-source.json](../sdk-source.json). Соответствие исходному ABI не является подтверждением совместимости жизненного цикла клиента.

> **Не устанавливайте пример в текущий MandaGram как поддерживаемый плагин.** Клиент загружает и выгружает библиотеки при чтении метаданных и отключении плагинов, а Kotlin/Native встраивает runtime. У ABI нет протокола его остановки. Подробности — в разделе [«Жизненный цикл и безопасность»](#жизненный-цикл-и-безопасность).

## Инструменты

Установите официальную [дистрибуцию Kotlin/Native 2.1.21](https://github.com/JetBrains/kotlin/releases/tag/v2.1.21) `kotlin-native-prebuilt-windows-x86_64-2.1.21.zip`. Нужен Native compiler, а не только JVM `kotlinc`. Укажите каталог распакованной дистрибуции в `KOTLIN_NATIVE_HOME`; скрипт проверяет версию компилятора.

Нужна Java для запуска инструментов Kotlin/Native; используйте JDK 17 и настройте `JAVA_HOME`/`PATH`. При первом запуске Kotlin/Native скачивает собственные зависимости, поэтому требуются сеть и доступный для записи каталог кеша (обычно `%USERPROFILE%\.konan`). Общие требования описаны в [документации Kotlin/Native](https://kotlinlang.org/docs/native-get-started.html).

Скрипт запускайте на Windows x64. Gradle, JVM хоста и JNI-мост для полученной библиотеки не нужны.

## Windows

PowerShell из корня репозитория:

```powershell
$env:KOTLIN_NATIVE_HOME = 'C:\Tools\kotlin-native-prebuilt-windows-x86_64-2.1.21'
.\build.ps1
```

Либо передайте путь явно:

```powershell
.\build.ps1 -KotlinNativeHome 'C:\Tools\kotlin-native-prebuilt-windows-x86_64-2.1.21'
```

Результаты — `build/mingw_x64/`: привязки `mandagram.klib` и DLL примера Plain Text, а также вспомогательные файлы компилятора. DLL — нативная x64 библиотека, не JVM JAR.

## Повторно используемый SDK

[interop/mandagram.def](../interop/mandagram.def) задаёт пакет `mandagram.c`. `cinterop` читает [канонический C-заголовок](../include/mandagram_plugin.h) и создаёт target-specific `mandagram.klib`. SDK не содержит реализацию клиента и не требует линковки с его библиотекой: адреса функций передаются хостом через `PluginApi`.

Привязки включают `PluginApi`, `PluginMetadata`, `HookParam`, все типы callback и все **53 слота** таблицы, не только функции примера:

| Слоты | Группа |
| --- | --- |
| 0–8 | Core Engine: hooks, logging, paths, user/chat IDs, TDLib |
| 9–16 | Low-level Compose Runtime Primitives |
| 17–20 | Update, message send/receive, chat action hooks |
| 21–34 | Object/field reflection, strings, attached fields, state |
| 35–45 | Compose modifiers |
| 46–52 | Compose components и avatar bitmap |

Порядок, выравнивание и C-типы определяет `cinterop` по заголовку, а не вручную продублированная Kotlin-структура. `int64_t` отображается в `Long`, `uint32_t` — в `UInt`, `uintptr_t` на Windows x64 — в `ULong`, C `bool` — в `Boolean`. `jobject` остаётся непрозрачным указателем, не Kotlin/JVM-объектом. Наличие слота не обещает доступность UI-функции или иной возможности клиента: сверяйте её реализацию в закреплённой ревизии.

Политика генерации: `headers` и `headerFilter` в `.def` выбирают весь `mandagram_plugin.h`; списков исключённых функций или сокращённой таблицы нет. Поля function pointer остаются C-указателями с nullable-значением и вызываются через `invoke` после проверки наличия. `const char*` в callback — `CPointer<ByteVar>?`: const не выражает владение в Kotlin, поэтому не изменяйте заимствованную память. `void*`/`jobject` — непрозрачные указатели, `void**` — указатель на массив указателей, `float` — `Float`; типы и padding `HookParam` также берутся из заголовка. Не заменяйте эти типы JVM-ссылками и не упаковывайте структуры вручную.

Можно сгенерировать только SDK, без примера:

```powershell
New-Item -ItemType Directory -Force build/mingw_x64 | Out-Null
& "$env:KOTLIN_NATIVE_HOME/bin/cinterop.bat" -def interop/mandagram.def `
    -compiler-option "-I$PWD/include" -target mingw_x64 `
    -o build/mingw_x64/mandagram
```

Для собственного Windows DLL-плагина импортируйте `mandagram.c.*` и `kotlinx.cinterop.*`, включите `ExperimentalForeignApi`, а для прямых экспортов `@CName` — `kotlin.experimental.ExperimentalNativeApi`, как в примере. Подключите `mandagram.klib` для `mingw_x64`, созданную той же версией Kotlin/Native 2.1.21. Например, если ваш исходник называется `MyPlugin.kt`:

```powershell
& "$env:KOTLIN_NATIVE_HOME/bin/kotlinc-native.bat" MyPlugin.kt `
    -library build/mingw_x64/mandagram.klib -target mingw_x64 `
    -produce dynamic -opt -o build/mingw_x64/my_plugin
```

Для отдельного downstream-проекта скопируйте `mandagram.klib` в его каталог зависимостей и замените путь после `-library` на этот файл; исходник Plain Text подключать не нужно. Реализуйте оба прямых экспорта с сигнатурами из следующего раздела и соблюдайте то же ограничение на выгрузку runtime. `mandagram.klib` — вход компилятора, не файл для установки в каталог плагинов; при распространении сохраняйте сведения о версии Kotlin/Native, цели `mingw_x64` и закреплённой ревизии заголовка. Сгенерированные заголовки/таблицы символов Kotlin/Native также не заменяют ABI MandaGram.

## Экспорты и пример

[examples/PlainText.kt](../examples/PlainText.kt) — отдельный потребитель klib; его логика реализована в Kotlin, без C-реализации callback. Пример экспортирует непосредственно через `kotlin.native.CName` и opt-in `ExperimentalNativeApi`:

- `mandagram_plugin_metadata`: возвращает указатель на `PluginMetadata`;
- `mandagram_plugin_init`: принимает указатель на `PluginApi`, возвращает C `bool`.

Хост должен разрешать именно эти два имени через системный загрузчик, а не обращаться к сгенерированной Kotlin-таблице `*_symbols()`. Все четыре UTF-8 C-строки и структура метаданных выделены один раз через `nativeHeap`, хранятся в статическом свойстве и не освобождаются: ABI не задаёт shutdown и владение этими указателями остаётся у плагина. Нельзя возвращать метаданные из `memScoped` или освобождать их в хосте.

`pluginInit` проверяет указатель таблицы и наличие `register_message_send_hook`, регистрирует `staticCFunction(::beforeSend)` с пустым after-callback и `user_data = 0`. Нулевой результат регистрации означает успех, любой другой — `false`. Ссылка на callback не захватывает Kotlin-объекты; `StableRef` не нужен.

Callback сравнивает семь байт точного ASCII-префикса `.plain ` последовательно, с short-circuit: несовпадение или NUL прекращает чтение. При совпадении возвращается исходный указатель плюс семь байт, иначе исходный указатель, в том числе null. Нет декодирования в Kotlin `String`, копирования текста, создания буфера или выделения памяти на каждое сообщение. Метаданные выделяются отдельно от callback, а Kotlin/Native по-прежнему имеет собственный runtime и GC.

Входная строка и возвращаемая подстрока **заимствованы**; хост копирует результат до завершения обработки вызова. Плагин не сохраняет указатель, не меняет вход и не освобождает его. `.plain ` без текста возвращает указатель на завершающий NUL; пустая строка не означает отмену отправки. Это не экранирование содержимого: результат с `{"@type":` может интерпретироваться клиентом как структурированный контент.

В собственных плагинах соблюдайте время жизни указателей, opaque handles и callback. Не выпускайте Kotlin-исключения через C ABI. `staticCFunction` должен указывать на незахватывающую функцию с точной C-сигнатурой; не передавайте замыкания с локальным состоянием.

## Жизненный цикл и безопасность

ABI закреплённой ревизии содержит 53 слота, но не содержит согласования версии, deinit/shutdown или unregister. Код SDK должен соответствовать клиенту: добавленная проверка null не позволяет безопасно читать слот за границей более короткой таблицы.

Текущий клиент может загрузить библиотеку для чтения метаданных и затем выгрузить её; отключение плагина также сопровождается выгрузкой. Вызов Kotlin-экспорта инициализирует встроенный runtime, который может иметь потоки и внутреннее состояние. Освобождение DLL через `FreeLibrary` не является корректным протоколом остановки этого runtime. Поэтому **обычный просмотр метаданных, установка, отключение и повторная загрузка этого Kotlin-плагина в текущем MandaGram не поддерживаются**. Успех отдельного вызова не доказывает безопасность последующей выгрузки. Постоянные nativeHeap-метаданные это ограничение не исправляют.

Здесь нет клиентских изменений, самозакрепления библиотеки в памяти или флагов загрузчика, маскирующих проблему. Для поддержки в клиенте нужен отдельно согласованный жизненный цикл runtime и зарегистрированных callback. Не обходите ограничение на рабочем аккаунте.

Для изолированной ABI-проверки используйте отдельный свежий host-процесс на каждый сценарий: загрузите DLL, разрешите оба прямых экспорта, прочитайте метаданные, вызовите init с корректной 53-слотовой таблицей, сохраните зарегистрированный callback и вызовите его на граничных строках. Проверьте точный возвращённый указатель, отказ регистрации и отсутствие функции регистрации. **Не вызывайте `FreeLibrary` и не перезагружайте библиотеку; завершите тестовый процесс, оставив модуль загруженным.** Такой эксперимент проверяет только ABI и callback, не работу жизненного цикла MandaGram.

Нативный плагин исполняется внутри процесса без песочницы; чтение метаданных уже может исполнить его код. Не загружайте неизвестные DLL. Не используйте рабочие данные, аккаунты или базы клиента для экспериментов.

## Статус проверки

Windows x64 DLL собрана Kotlin/Native **2.1.21** и проверена отдельным C++ host-процессом: разрешены точные экспорты `mandagram_plugin_metadata` и `mandagram_plugin_init`, проверены стабильные метаданные, null-указатель API, отсутствующий слот регистрации, отказ регистрации, 11 граничных вариантов текста (включая null), точные заимствованные указатели результата и callback с другого нативного потока. Модуль не выгружался.

При сборке компилятор сообщил предупреждения об отсутствующем `return` в сгенерированном им `api.cpp`. Это не исходник SDK; предупреждения не подавлялись и не означают, что сборка прошла без замечаний. Проверка фактических прямых экспортов и вызовов DLL прошла успешно; она не доказывает корректность всех вспомогательных экспортов компилятора.

Проверка загрузки в MandaGram не заявляется. Сборка DLL и изолированная проверка ABI не подтверждают безопасность выгрузки или совместимость с произвольной версией клиента.
